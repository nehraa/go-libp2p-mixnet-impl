What is libp2p?

Understanding the building blocks of peer-to-peer networking

The P2P Networking Challenge

Building peer-to-peer applications is hard. You need to find peers, connect to them, prove who they are, and send data — all without a central server.

libp2p solves this by providing a modular networking stack that handles all the hard parts. Think of it as the "operating system" for P2P apps.

The libp2p Stack

Your node's identity and main API — think of it as your P2P profile

↓

Network

↓

Actual wire protocols: TCP, WebSocket, QUIC, etc.

Why This Matters for AI Steering

When you tell AI "build a P2P chat app," it needs to know which layer handles what. Put crypto logic in Transport? Wrong. Handle peer discovery in Network? Right. Understanding the stack helps you catch architectural mistakes before they become bugs.

Peer Identity

Your cryptographic passport on the P2P network

What is a Peer ID?

In libp2p, identity is cryptographic. Your Peer ID proves you are who you say you are, and nobody can impersonate you without stealing your private key.

Peer ID Generation

🔑

Private Key

→
🔓

Public Key

→
#

Hash

→
ID

Peer ID

Here's how it works: You generate a key pair. The public key gets hashed using SHA-256. That hash becomes your Peer ID. It's like a fingerprint — unique to you and impossible to reverse-engineer back to your key.

Peer ID in Code

// From core/peer/peer.go

// ID is a libp2p peer identity
// Derived by hashing a peer's public key
type ID string

func IDFromPublicKey(pk ic.PubKey) (ID, error) {
    // Marshal to bytes then hash
    b, err := pk.Bytes()
    if err != nil {
        return "", err
    }

    // Hash using SHA-256
    hash, _ := mh.Sum(b, mh.SHA2_256, -1)
    return ID(hash), nil
}

The Process Unpacked

1. Get public key: Start with your public key that pairs with your private key.

2. Convert to bytes: Serialize the key into raw bytes that can be hashed.

3. Hash it: Use SHA-256, a one-way hash function. This is your Peer ID - you can't reverse it to get the original key.

Result: A 46-character string starting with "Qm" (like QmYy...3k7i) that uniquely identifies you on the network.

Why This Design?

User

Can someone pretend to be me by guessing my Peer ID?

libp2p

No! Your Peer ID is public. But to PROVE you're that Peer ID, you need the private key. Every connection includes cryptographic proof.

Explained in: id.MatchesPrivateKey(sk)

User

What if I lose my private key?

libp2p

You lose your identity. There's no central authority to recover it. Backup your keys! This is how decentralization works.

No recovery mechanism exists

Verification Without Exposure

The Peer ID contains your public key (in small keys) or its hash (for larger keys). When someone connects, they verify by checking: "Does the public key hash to this Peer ID?" Then a challenge-response proves you own the private key. Your private key NEVER leaves your machine.

Your app generates a key pair. Can you change the Peer ID while keeping the same key?

A. Yes, Peer IDs are configurable

B. No, the Peer ID is deterministically derived from the public key

C. Only if you rehash with a different algorithm

03

Cryptographic Keys

The foundation of trust in P2P networks

Key Types in libp2p

libp2p supports multiple key algorithms. Each has tradeoffs in security, speed, and key size.

E Ed25519 (Recommended)

Fast, secure, small keys. Modern elliptic curve cryptography. Signatures are compact, verification is quick. Best for most applications.

R RSA (Legacy)

Large keys (2048+ bits). Battle-tested but slower. Use only if required by external systems that mandate RSA.

S Secp256k1

Bitcoin/Blockchain standard. Same curve used for Bitcoin addresses. Good for crypto-native applications.

EC ECDSA

Elliptic curve with various curves. Good for compatibility with existing PKI systems.

Key Interfaces

// From core/crypto/key.go

// Key is the common interface for all keys
type Key interface {
    Equals(Key) bool
    Raw() ([]byte, error)
    Type() pb.KeyType
}

// PrivKey represents a private key
type PrivKey interface {
    Key
    Sign([]byte) ([]byte, error)
    GetPublic() PubKey
}

// PubKey represents a public key
type PubKey interface {
    Key
    Verify(data []byte, sig []byte) (
        bool, error)
}

The Key Abstraction

Key interface: All keys can compare for equality, export raw bytes, and report their type.

PrivKey: Can Sign data (proving ownership) and derive the corresponding PubKey.

PubKey: Can Verify that a signature was created by the matching private key.

This abstraction lets libp2p support multiple algorithms with the same interface. Your app doesn't care if it's RSA or Ed25519 — it just calls Sign() and Verify().

Sign and Verify

Alice

I'm sending you a message! Here's my signature...

msg + signature over hash(msg)

Bob

Let me verify... hash(msg) matches, signature valid. This really came from Alice!

pubKey.Verify(hash(msg), signature)

This is what happens on every libp2p connection. Your keys prove your identity without revealing anything sensitive.

Why is Ed25519 preferred over RSA for new libp2p applications?

A. Smaller keys, faster signatures, same security level

B. RSA is broken and insecure

C. Ed25519 is required by the libp2p specification

04

The Host

Your node's main entry point — the "face" of your P2P application

What is a Host?

The Host is your application's P2P persona. It's both a server (listening for incoming connections) and a client (connecting to other peers).

The Name Matters

It's called "Host" (not "Client" or "Server") because every node is both. In P2P, there's no distinction between clients and servers — everyone can initiate and receive connections.

The Host Interface

// From core/host/host.go

type Host interface {
    // Identity
    ID() peer.ID
    Addrs() []ma.Multiaddr

    // Connections
    Connect(ctx context.Context, pi peer.AddrInfo) error
    Network() network.Network

    // Protocols
    SetStreamHandler(pid protocol.ID, handler network.StreamHandler)
    NewStream(ctx context.Context, p peer.ID, pids ...protocol.ID) (network.Stream, error)

    // Lifecycle
    Close() error
}

What a Host Can Do

ID(): Returns your Peer ID — who you are on the network.

Addrs(): Your listen addresses where peers can reach you.

Connect(): Dial another peer, establishing a connection.

SetStreamHandler(): Register a handler for incoming data on a protocol.

NewStream(): Open a stream to another peer for sending data.

Network(): Access the underlying Network for advanced operations.

The Complete Flow

Set Handler

→

Connect

→

Stream

// Real code from the codebase
func main() {
    // 1. Create host
    h, _ := libp2p.New(
        libp2p.ListenAddrStrings("/ip4/127.0.0.1/tcp/0"),
    )

    // 2. Handle incoming
    h.SetStreamHandler("/chat/1.0.0", func(s network.Stream) {
        // Handle incoming data
    })

    // 3. Connect to peer
    h.Connect(ctx, peer.AddrInfo{
        ID: targetPeer,
        Addrs: addrs,
    })

    // 4. Open stream
    s, _ := h.NewStream(ctx, targetPeer, "/chat/1.0.0")
    s.Write([]byte("Hello!"))
}

Four-Step Pattern

1. Create: Initialize with listen addresses. The "/tcp/0" means "choose any available port."

2. Listen: Register handlers for protocols. Like setting up URL routes in a web server.

3. Connect: Dial the peer. This establishes an encrypted, authenticated connection.

4. Communicate: Open streams within the connection. Each stream is like a separate conversation.

The Network Layer

Managing connections, streams, and connectivity state

Network Responsibilities

While the Host is your high-level API, the Network does the heavy lifting: managing connections, tracking peer connectivity, and coordinating with Transports.

Connection State Machine

NotConnected

No connection, no info

→

Limited

Relay or partial

→

Connected

Direct, full connection

The Network Interface

// From core/network/network.go

type Network interface {
    // Core connection management
    DialPeer(ctx context.Context, p peer.ID) (Conn, error)
    ClosePeer(p peer.ID) error

    // Connection queries
    Connectedness(p peer.ID) Connectedness
    Peers() []peer.ID
    Conns() []Conn
    ConnsToPeer(p peer.ID) []Conn

    // Stream handling
    NewStream(ctx context.Context, p peer.ID) (Stream, error)
    SetStreamHandler(handler StreamHandler)

    // Listening
    Listen(...ma.Multiaddr) error
    ListenAddresses() []ma.Multiaddr

    // Notifications
    Notify(Notifiee)
    StopNotify(Notifiee)
}

Network Operations

DialPeer: Initiates connection to a specific peer. Coordinates with Transports to find the best path.

Connectedness: Returns state: NotConnected, Connected, or Limited (through relay).

Peers/Conns: Lists all connected peers and active connections. Useful for building peer lists.

Notify: Register callbacks for connection events — get notified when peers connect/disconnect.

The Network is what makes the Host work. It abstracts over multiple transports and manages the complexity of P2P connectivity.

Streams vs Connections

C Connection

The underlying transport link to a peer. Think of it as a single pipe that can carry multiple conversations.

S Stream

A multiplexed channel within a connection. One connection can have many streams — each protocol gets its own stream, all sharing the same pipe.

The Multiplexing Advantage

Without multiplexing, you'd need one connection per protocol. With it, you open one connection, then create streams for chat, file transfer, and control messages. It's like having multiple apps on your phone share one WiFi connection.

Host

I need to send chat data AND check the DHT for new peers...

Network

✓ You have one connection to peer X. Opening 2 streams: /chat/1.0.0 and /ipfs/kad/1.0.0

Both streams multiplexed over single connection

B. One connection, multiple streams — /file-list/1.0 and /file-sync/1.0

Transport Layer

Getting bits across the wire — TCP, QUIC, WebSocket, and more

What is a Transport?

Transports are the bottom of the stack — they actually move bytes between machines. libp2p abstracts over them, so your app doesn't care if it's TCP, QUIC, or carrier pigeon.

TCP TCP

Reliable, ordered, ubiquitous. The default for most libp2p nodes. Works everywhere but has head-of-line blocking.

QC QUIC

Built on UDP, built-in encryption (TLS 1.3), faster handshake. The future of P2P networking. Multiplexes natively.

WS WebSocket

Runs over HTTP, works through corporate firewalls and proxies. Essential for browser-based nodes.

WSS WebRTC

Direct browser-to-browser. NAT traversal built-in. For true P2P in web browsers.

The Transport Interface

// From core/transport/transport.go

type Transport interface {
    // Dial a remote peer
    Dial(ctx context.Context, raddr ma.Multiaddr, p peer.ID) (CapableConn, error)

    // Can this transport dial this address?
    CanDial(addr ma.Multiaddr) bool

    // Listen for connections
    Listen(laddr ma.Multiaddr) (Listener, error)

    // What protocols does this transport support?
    Protocols() []int
}

Transport Contract

Dial: Connect to a peer at a specific address. Returns a "capable connection" — one that's upgraded with security and multiplexing.

CanDial: Check if this transport can handle this address. TCP transport returns true for /tcp/ addresses.

Listen: Start accepting incoming connections on a local address.

Protocols: Report which multiaddr protocols this transport understands.

Pluggable by Design

You can add new transports without changing your app code. Just import the transport package and libp2p auto-detects it. Your app uses the "Capability" interface — it doesn't care if it's TCP, QUIC, or something custom.

Multiaddr: Self-Describing Addresses

Multiaddr Example

/ip4/192.168.1.10/tcp/4001/p2p/QmYy...

Each segment describes one layer: IP → TCP → libp2p peer

Multiaddrs are a key insight: they're protocol-agnostic, composable, and self-describing. The address tells you exactly how to reach a peer: use IPv4, then TCP, then the libp2p protocol with that Peer ID.

Peer Discovery

Finding peers without a central directory

The Discovery Problem

P2P apps need to find peers before they can connect. But without a central server, how? libp2p provides multiple discovery mechanisms.

New Node

I just joined the network. How do I find peers?

DHT

Ask me! I maintain a distributed hash table of who's online.

Kademlia DHT protocol

mDNS

Or check locally — if you're on the same WiFi, I can find nearby peers instantly.

Multicast DNS for LAN discovery

Discovery Interfaces

// From core/discovery/discovery.go

// Advertiser announces services
type Advertiser interface {
    Advertise(ctx context.Context, ns string, opts ...Option) (
        time.Duration, error)
}

// Discoverer finds peers providing a service
type Discoverer interface {
    FindPeers(ctx context.Context, ns string, opts ...Option) (
        <-chan peer.AddrInfo, error)
}

// Discovery combines both
type Discovery interface {
    Advertiser
    Discoverer
}

The Discovery Contract

Advertise: Announce "I provide service X" so others can find you. Returns TTL — how long the advertisement is valid.

FindPeers: Search for peers providing a service. Returns a channel that yields peers as they're found. This is asynchronous because discovery takes time.

Namespace: The "ns" parameter is like a service name — "/myapp/1.0.0" identifies your app's peers.

Debug Checklist

When your P2P app isn't working, check these layers from top to bottom:

1. Identity: Does peer.ID() return what you expect?
   h.ID().String() // Should be a valid Peer ID

2. Listening: Is the host accepting connections?
   h.Addrs() // Shows listen addresses

3. Connectivity: Can you reach the peer?
   h.Network().Connectedness(peerID) // Should be Connected

4. Streams: Can you open a stream?
   s, err := h.NewStream(ctx, peerID, protocol) // Check err

5. Discovery: Is the DHT finding peers?
   peers, err := dht.FindPeers(ctx, ns) // Check channel output

Debugging Strategy

Start at the bottom of the stack. Can't connect? Check addresses. Can connect but no stream? Check protocols. Can open stream but no data? Check your handler registration. Layer-by-layer debugging isolates problems.
