What is the P2P Hub?

Understanding how peer-to-peer applications manage connections, streams, and communication

The Problem: Managing P2P Connections

When you build a peer-to-peer application, every peer can connect directly to every other peer. This creates a challenge: how do you manage all these connections?

The Hub solves this by acting as a postal service for your P2P network. Just like a post office manages mail delivery to multiple addresses, the Hub manages data delivery to multiple peers.

The Two Main Characters

H The Hub

The central coordinator that manages all peer connections. It creates and tracks receptors, handles stream lifecycle, and publishes events about what's happening.

R The Receptor

A binding between the Hub and a specific peer. Each receptor manages one active stream and tracks connection health through pings.

Why This Matters for AI Steering

When you tell AI to "add peer-to-peer messaging to my app," you need to know that managing multiple connections requires a coordination layer. Without understanding this concept, AI might create brittle code that doesn't handle reconnection, backpressure, or concurrent streams.

Creating a Receptor

// From hub.go
func (h *Hub) CreateReceptor(
    ctx context.Context,
    target peer.AddrInfo,
) (*Receptor, error) {
    // Prevent duplicate bindings
    if _, exists := h.receptorsByPeer[
        target.ID]; exists {
        return nil, ErrDuplicatePeerBinding
    }

    receptorID := ReceptorID(fmt.Sprintf(
        "receptor-%d", h.nextID.Add(1)))
    receptor := newReceptor(h, receptorID, target)

    h.receptorsByID[receptorID] = receptor
    h.receptorsByPeer[target.ID] = receptor

    // Start health check pings
    go receptor.runPingLoop()

    return receptor, nil
}

What's Happening Here

1. Check duplicates: Can't have two receptors to the same peer - that would be like having two phone lines to the same friend.

2. Create receptor: A new Receptor struct is initialized with a unique ID and target peer info.

3. Track it: Store in two maps - one by ID for quick lookup, one by peer ID.

4. Start pings: Launch a background goroutine that periodically checks connection health.

The Receptor's State Machine

Each Receptor tracks detailed metrics that help you understand the health of peer connections:

type Receptor struct {
    hub                 *Hub           // Parent hub reference
    id                  ReceptorID     // Unique identifier
    target              peer.AddrInfo  // Who we're connected to
    activeStream        network.Stream // Current data stream
    activeDirection     network.Direction // Inbound or outbound

    // Metrics (all tracked per-Receptor)
    bytesSent           uint64
    bytesReceived       uint64
    connectAttemptCount uint64
    connectFailureCount uint64
    streamOpenCount     uint64
    pingSuccessCount    uint64
    pingFailureCount    uint64
}

The Power of Metrics

Why track all these numbers? Because in production, you'll need to answer questions like: "Is this peer slow?" (RTT), "Did they receive my data?" (bytesReceived), "Is the connection stable?" (pingFailureCount). The Receptor maintains this state so your app can make smart decisions.

Sending Data: The Send Method

// From receptor.go
func (r *Receptor) Send(
    ctx context.Context,
    payload []byte,
) (int, error) {
    r.mu.RLock()
    stream := r.activeStream
    r.mu.RUnlock()

    if stream == nil {
        return 0, ErrNoActiveStream
    }

    // Apply deadline if context has one
    if deadline, ok := ctx.Deadline(); ok {
        stream.SetWriteDeadline(deadline)
        defer stream.SetWriteDeadline(time.Time{})
    }

    n, err := stream.Write(payload)
    if err != nil {
        r.handleStreamWriteError(stream, err)
        return n, err
    }

    r.recordSend(n)  // Track metrics
    return n, nil
}

The Flow Explained

1. Get stream safely: Use a read-lock to get the current stream - another goroutine might be changing it.

2. Check exists: If no stream, can't send. Return an error the caller can handle.

3. Set deadline: If the context times out, the write should also timeout. This prevents hanging.

4. Write: Actually write to the network stream. This is where data leaves your computer.

5. Track: Update bytesSent counter so metrics reflect reality.

Receiving Data: The Read Loop

Each Receptor runs a read loop in a background goroutine. This loop continuously reads from the stream and emits events.

// From receptor.go
func (r *Receptor) runReadLoop(stream network.Stream) {
    buffer := make([]byte, r.hub.cfg.ReadBufferSize)
    for {
        n, err := stream.Read(buffer)
        if n > 0 {
            chunk := append([]byte(nil),
                buffer[:n]...)
            snapshot, firstPacket, _ :=
                r.recordInbound(stream, n)

            r.hub.emitEvent(Event{
                Kind:      EventKindDataReceived,
                Data:      chunk,
                Snapshot:  snapshot,
                IsFirstPacket: firstPacket,
            })
        }

        if err != nil {
            // Stream closed or error
            r.hub.emitEvent(Event{
                Kind: EventKindStreamClosed,
            })
            return
        }
    }
}

Reading Continuously

Infinite loop: Keeps reading until the stream closes or errors.

Buffer & copy: Read into a buffer, then copy to a new slice. The copy is necessary because the buffer gets reused.

Emit event: Your application receives data through the Hub's Events() channel. This is how you get notified.

First packet flag: Special marker for the very first data received - useful for connection establishment protocols.

Events & Observability

How the Hub tells you what's happening in real-time

The Event System

The Hub communicates with your application through two channels: Events (what happened) and Metrics (performance data). Think of Events as a news feed and Metrics as analytics.

const (
    EventKindReceptorCreated  EventKind = "receptor_created"
    EventKindReceptorRemoved  EventKind = "receptor_removed"
    EventKindStreamOpened     EventKind = "stream_opened"
    EventKindStreamClosed     EventKind = "stream_closed"
    EventKindDataReceived     EventKind = "data_received"
    EventKindPeerOffline      EventKind = "peer_offline"
    EventKindError            EventKind = "error"
)

Listening for Events

// Your application
func handleEvents(hub *hub.Hub) {
    for evt := range hub.Events() {
        switch evt.Kind {
        case hub.EventKindDataReceived:
            processData(evt.Data, evt.PeerID)
        case hub.EventKindStreamClosed:
            log.Printf("Stream to %s closed",
                evt.PeerID)
        case hub.EventKindPeerOffline:
            // Trigger reconnection logic
            reconnect(evt.PeerID)
        }
    }
}

Reacting to the Hub

Range over Events(): This channel receives every significant thing the Hub does.

Switch on Kind: Different events need different responses. Data received? Process it. Stream closed? Maybe reconnect. Peer offline? Trigger recovery.

Snapshots: Every event includes a Snapshot - a complete picture of the Receptor's state at that moment.

Handling Overflow: Backpressure

What if your app can't keep up with events? The Hub has configurable backpressure handling.

// From hub.go - handleEventOverflow
func (h *Hub) handleEventOverflow(evt Event) {
    receptor := h.receptorByPeerID(evt.PeerID)

    switch h.cfg.EventOverflowPolicy {
    case OverflowPolicyResetStream:
        // Aggressive: reset the stream
        // to stop data flow
        receptor.handleEventOverflow(evt, policy)
        h.emitMetric(MetricKindBackpressure, ...)

    case OverflowPolicyDrop:
        // Passive: just drop the event
        receptor.recordEventDrop()
        h.emitMetric(MetricKindEventDropped, ...)
    }
}

Managing Overload

ResetStream (aggressive): If your app can't keep up, terminate the stream. This signals the remote peer to stop sending. Good for preventing memory exhaustion.

Drop (passive): Silently discard events when buffer is full. The stream stays open but you lose data. Good for loss-tolerant applications.

Metrics: Either way, you get metrics (EventDropped or Backpressure) so you can observe this in production.

When AI Gets This Wrong

Many AI-generated P2P implementations don't handle backpressure - they just buffer infinitely until your app crashes. This Hub gives you two options and makes the overflow behavior observable. When steering AI, ask: "What happens if events pile up faster than I can process them?"

Key Patterns Summary

1 Lifecycle Management

Hub → CreateReceptor → use → RemoveReceptor/Close. Always clean up resources.

2 Event-Driven

Listen to Events() in a goroutine. React to lifecycle, data, and errors.

3 Stream Health

Use ping metrics to detect stalls. Reconnect on StreamClosed if needed.

4 Backpressure

Configure overflow policy based on your data criticality.

Debugging Checklist

When things aren't working, here's where to look:

// Common debugging patterns

// 1. Check if receptor exists
snapshot, err := hub.Snapshot(receptorID)
if err != nil {
    log.Printf("Receptor not found: %v", err)
}

// 2. Check stream health
if !snapshot.HasActiveStream {
    log.Println("No active stream - needs OpenStream")
}

// 3. Check peer connectivity
connectedness := snapshot.Connectedness
latency := snapshot.LastRTT

// 4. Monitor event drops
if snapshot.EventDropCount > 0 {
    log.Printf("Events dropped: %d",
        snapshot.EventDropCount)
}

Debug Strategy

1. Receptor exists? Check the Snapshot. If ErrReceptorNotFound, the Receptor was never created or was already removed.

2. Stream active? HasActiveStream tells you if data can flow. If false, you need OpenStream() or the stream was closed remotely.

3. Peer connected? Connectedness and LastRTT show network health. NotConnected means the peer is unreachable.

4. Events dropping? EventDropCount indicates backpressure. Your app isn't consuming events fast enough.
