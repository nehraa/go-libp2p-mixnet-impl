P2P System Integration
01

The Three Pillars

Hub, Upload, and Download work together to create a complete peer-to-peer file sharing system

The Architecture at a Glance

Imagine you want to share a large file with friends, but the file is too big to send in one piece. You also want multiple friends to help distribute it. This system solves that through three specialized packages:

🔌
Hub (p2p/hub)

The Hub manages peer connections. It's the foundation everything else builds on.

📤
Upload (p2p/upload)

The Upload package sends files. It shards data and distributes to peers using the Hub.

📥
Download (p2p/download)

The Download package retrieves files. It fetches shards in parallel and reconstructs them.

How They Connect

The relationship is hierarchical: Hub provides the low-level connection management, Upload and Download build higher-level file transfer on top.

📤
Upload Uses Hub
📥
Download Uses Hub
🔌
Hub Foundation
🌐
libp2p Network Layer

Upload and Download both sit on top of Hub, which sits on libp2p

💡
The Pattern: Separation of Concerns

Each package has one job and does it well. Hub doesn't know about files — it only manages streams. Upload doesn't know about downloads. This modularity makes the system maintainable and testable.

02

The Hub: Foundation Layer

Managing peer connections, streams, and message routing

What the Hub Provides

The Hub is a receptor-centric connection manager. Think of it as your phone system: it maintains a line open to each friend you might call.

📞

Peer Bindings

Creates and maintains Receptors — one per peer. Each Receptor tracks its connection state, latency, and statistics.

🔄

Stream Lifecycle

Opens, monitors, and resets streams automatically. Handles reconnections when connections drop.

📡

Event Pipeline

Delivers data-received and stream-closed events to Upload/Download managers through Go channels.

📊

Metrics

Tracks bytes sent/received, connection attempts, failures, latency EWMA — all per-receptor.

The Hub-Receptor Relationship

When Upload or Download wants to talk to a peer, they ask the Hub for a Receptor:

CODE 
// Hub creates and tracks Receptors
type Hub struct {
 receptorsByID   map[ReceptorID]*Receptor
 receptorsByPeer map[peer.ID]*Receptor
}

// Upload asks Hub for a Receptor
receptor, err := hub.CreateReceptor(ctx, peerInfo)

// Later, send data through it
receptor.Send(ctx, payload)
PLAIN ENGLISH

Hub keeps two lookup tables — one by ID, one by peer ID...

These let the Hub quickly find any Receptor it has...

They're mappings (dictionaries) from IDs to Receptor objects...

Upload code asks Hub to create a binding to a specific peer...

Receptor is like getting a dedicated phone line to that peer...

Once you have the Receptor, you can send bytes through it...

The Receptor handles the actual stream management...

03

Upload: Sending Files Out

The upload package distributes shards to multiple peers using the Hub

Two Sides of Upload

Upload has two distinct modes: sending (Manager) and receiving (Receiver). Both use the Hub — but differently:

1
Manager — uses Hub for sending

The Upload Manager creates Hub Receptors to each destination peer. It sends shards through these receptors and waits for acknowledgments (acks).

2
Receiver — uses Hub for receiving

The Upload Receiver registers a stream handler directly with libp2p. When peers connect to upload, the Hub routes those incoming streams to the Receiver.

Manager Uses Hub.Receptor

The Upload Manager creates a Hub instance and asks it for Receptors to each holder peer:

CODE 
func NewManager(h host.Host, r routing.Routing, cfg Config) (*Manager, error) {
 // ... config setup ...
 
 // Create Hub with our protocol ID
 hubCfg := normalized.HubConfig
 hubCfg.ProtocolID = normalized.ProtocolID
 hb, err := hub.New(h, hubCfg)
 
 manager := &Manager{
 hub: hb, // Store Hub reference
 }
 
 // Later: create receptor for each holder
 receptor, err := manager.hub.CreateReceptor(ctx, holder)
PLAIN ENGLISH

Constructor for Upload Manager — takes a libp2p host...

Skip over the configuration normalization details...

Prepare Hub configuration, using same protocol ID...

This ensures Upload and Download speak the same "language"...

Create the Hub instance, passing in the libp2p host...

Create the Manager struct instance...

Store the Hub reference so we can use it later...

When we're ready to upload to a specific peer...

Ask Hub to create/maintain a Receptor to that holder...

04

Download: Pulling Files In

The download package fetches shards and uses the Hub for peer communication

Download Architecture

Download mirrors Upload's pattern but in reverse: the Manager acts as the requester (using Hub), and HolderService acts as the responder (receiving requests via Hub).

📥
Download Manager

Uses Hub Receptors to connect to holder peers and request shards. It's a client using the Hub's requester-side API.

📤
HolderService

Uses Hub to accept incoming requests. It binds allowed requesters to Receptors and serves shard data through them.

HolderService Allows Requesters

Before a download can happen, the holder must explicitly allow the requester:

CODE 
func (s *HolderService) AllowRequester(
 ctx context.Context,
 requester peer.AddrInfo,
) error {
 // Create receptor through Hub
 receptor, err := s.hub.CreateReceptor(ctx, requester)
 
 // Store in allowed map
 s.mu.Lock()
 s.allowed[requester.ID] = receptor
 s.mu.Unlock()
}
PLAIN ENGLISH

Method to authorize a peer to download from us...

Receives context (deadline/cancellation) and peer info...

Peer info includes their ID and network addresses...

Returns error if something goes wrong...

Security: only explicitly allowed peers can download...

Ask Hub to create a Receptor to this requester...

Lock the mutex for thread-safe access...

Store receptor in allowed peers map...

Unlock so other goroutines can access...

🛡️
Security: Explicit Allowlisting

HolderService doesn't let just anyone download. The requester must be explicitly allowed first. This prevents unauthorized data leakage.

The Pattern: Composition

Notice how each layer doesn't duplicate functionality? Upload and Download don't implement their own peer connection logic — they compose with Hub. This is composition over inheritance in action.
