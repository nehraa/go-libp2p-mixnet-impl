What This Package Does

Distributed file downloading through parallel shard fetching and reconstruction — imagine downloading a movie not from one server, but from many friends' computers at once

The Big Picture

The download package is part of a peer-to-peer file sharing system. Instead of downloading a complete file from one source, it breaks files into smaller shards and downloads them in parallel from multiple sources.

1
File gets split into shards

A large file is divided into equal-sized pieces, each with a unique identifier and cryptographic fingerprint

2
Shards are distributed to holders

Each shard is stored on different computers (peers) in the network — like storing copies at different friends' houses

3
Download manager fetches shards in parallel

When you want the file back, the download manager reaches out to multiple holders simultaneously

4
Shards are verified and reconstructed

Each shard is checked for integrity, then assembled back into the original file

Why This Approach Works

🚀

Speed Through Parallelism

Download multiple shards simultaneously instead of waiting for one stream — like having multiple delivery trucks instead of one

🔒

Integrity Verification

Every shard is cryptographically hashed — any tampering is detected immediately, like a tamper-evident seal

🌐

No Single Point of Failure

If one holder is offline, others may still have the shards you need — distributed resilience

Meet the Actors

Four key players work together to make distributed downloading possible

The Cast of Characters

📥
Manager

The Manager orchestrates downloads. It's the requester side — the one asking for shards.

📤
HolderService

The HolderService serves shards to anyone who's allowed to ask. It's the responder side.

📋
ShardProvider

The ShardProvider interface abstracts where shards come from. The default implementation reads from files on disk.

🧩
ThresholdReconstructor

The ThresholdReconstructor rebuilds original files from partial shards using redundancy schemes (not shown in this implementation).

The Shard Receiver

When the Manager requests a shard, it creates a shardReceiver that handles incoming data chunks:

CODE 
func newShardReceiver(
 uploadID string,
 shardIndex int,
 descriptor ShardDescriptor,
 tempPath string,
) (*shardReceiver, error) {
 file, err := os.OpenFile(
 tempPath,
 os.O_CREATE|os.O_TRUNC|os.O_WRONLY,
 0o644,
 )
 return &shardReceiver{
 file: file,
 hasher: sha256.New(),
 done: make(chan struct{}),
 }, nil
}

The shard index tells us which piece this is (0, 1, 2, etc.)...

The descriptor contains expected size and hash for verification...

tempPath is where we'll write the shard while downloading...

Open the temp file for writing, creating it if needed...

OS flags: create, truncate, write-only mode...

File permissions: owner can read/write, others read-only...

Return the receiver struct we just built...

Store the open file handle to write chunks to...

Create a SHA-256 hasher to verify the downloaded data...

Create a channel to signal when downloading is complete...

The Wire Protocol

How computers agree on what messages mean

Frame Types

Communication happens through frames. Each frame has a kind byte indicating its purpose:

📤

PullRequest (0x11)

"Please send me shard #X from upload Y" — the opening request from Manager to Holder

📦

ShardChunk (0x12)

A piece of actual shard data with offset information for reassembly

✅

ShardEnd (0x13)

Marks the end of a shard transfer with total byte count

⚠️

Error (0x14)

Something went wrong — includes error message explaining what

Binary Encoding

Messages use binary encoding for efficiency. Here's how a pull request frame gets encoded:

CODE 
func encodePullRequestFrame(
 f pullRequestFrame,
) ([]byte, error) {
 uploadLen := len(f.UploadID)
 reqLen := len(f.RequestID)
 out := make([]byte,
 2+uploadLen+2+reqLen+4)
 pos := 0
 binary.BigEndian.PutUint16(
 out[pos:pos+2],
 uint16(uploadLen),
 )
PLAIN ENGLISH

Function to turn a pull request into raw bytes...

The frame contains UploadID, RequestID, and ShardIndex...

Calculate how much memory we need to allocate...

Total size = lengths (2 bytes each) + strings + shard index (4 bytes)...

Create a byte slice of exactly that size...

Start writing at position 0...

Write the upload ID length as 2 bytes in big-endian format...

Target the first 2 bytes of our buffer...

Convert Go's int to unsigned 16-bit for network compatibility...

💡
Key Insight

The big-endian format ensures any computer, regardless of architecture, can read the message correctly. This is one of those "agree on the rules" moments that make the internet work.

05

Security & Integrity

How do you know the file you got is the file you wanted?

The Manifest

Every upload has a manifest — a cryptographically signed document describing all shards. It includes:

1
Upload ID

A unique identifier for this specific upload

2
Total Shards

How many pieces the file was split into

3
Shard Descriptors

For each shard: index, holder peer ID, size, and SHA-256 hash

4
Cryptographic Signature

Proves the manifest came from the original uploader, not an imposter

Verification in Action

When a shard finishes downloading, the Manager validates it against the manifest:

CODE 
func (r *shardReceiver) handleEnd(
 frame shardEndFrame,
) {
 actualDigest := r.hasher.Sum(nil)
 if !digestEqual(actualDigest,
 r.descriptor.Digest) {
 r.finishLocked(fmt.Errorf(
 "%w: shard %d digest mismatch",
 ErrShardIntegrity,
 r.shardIndex,
 ))
 return
 }
 r.completed = true
}
PLAIN ENGLISH

Method called when we receive the "end of shard" frame...

The frame tells us how many bytes were sent total...

Compute the SHA-256 hash of everything we received...

Compare actual hash against the expected hash from manifest...

The expected digest was in the descriptor we saved earlier...

If hashes don't match, create an error explaining what failed...

Include the standard "integrity check failed" error type...

Also include which shard number failed for debugging...

End the error formatting...

Exit the function early — verification failed...

If we got here, hashes matched! Mark download complete...

🛡️
Security Principle

Trust But Verify: Even trusted peers could have corrupted files, network errors, or malicious actors. The manifest signature proves authorship; the hash proves integrity. Never skip verification.
